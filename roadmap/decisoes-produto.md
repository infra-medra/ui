# Decisões do produto — MedraUi

> Documento vivo. Cada item começa como "Pendente" e é atualizado conforme decidimos.
> Última atualização: 2026-07-03

## Fase 0 — Base legal e marca
- [x] **Nome, marca e domínio do novo produto** — **Decidido em 2026-07-02**: nome do produto é **MedraUi** (biblioteca de componentes da empresa Medra). Domínio `medra.dev` já é da empresa. Verificado: existe um "medra-ai" no GitHub, mas é empresa de robótica/IA industrial, mercado não relacionado (baixo risco de confusão). Nomes de pacote npm testados e disponíveis: `medra`, `medra-ui`, `medra-ng`, `@medra/ui`, `@medra/ng` (todos 404 no registry). **Formato do pacote resolvido na Fase 2**: `@medra/ui`. **Ainda pendente**: prefixo de seletor de componente Angular (ex.: `medra-button`? precisa confirmar).

## Fase 1 — Auditoria técnica
- [x] **Escopo da reescrita definido** — **Decidido em 2026-07-02**: não é só estilo/ícones — a lógica de cada componente (TypeScript/template/API) também será reescrita do zero. Cada componente é escrito com abordagem signal-first, sem copiar código de terceiros.
- [x] **Modelo de entrega do Tailwind no pacote** — **Decidido em 2026-07-02**: CSS pré-gerado e auto-contido, compilado no build da MedraUi. Consumidor não precisa ter Tailwind configurado no próprio app (funciona sozinho).
- [x] **Catalogar tokens de design** — **Levantado em 2026-07-02**, detalhado em `catalogo-tokens-design.md`. Achado-chave: a camada de cores primitivas é a paleta padrão do Tailwind (não precisa reconstruir). O trabalho real é a camada semântica (marca, superfície, campos de formulário, listas, navegação, overlays, foco/desabilitado — tudo com light/dark) e a camada por componente (severidade × variante de estilo × estado × tamanho × color scheme).
- [x] **Criar `tailwind.config` interno da MedraUi** — **Rascunho criado em 2026-07-02** em `tailwind-theme-medraui.css`. Decisão técnica tomada junto: **Tailwind v4**, config CSS-first via `@theme` (sem JS config), dark mode via `@custom-variant` consistente com a decisão de classe `dark` no elemento raiz. Cobre: cor de marca (placeholder), escala de superfície light/dark, radius, foco, desabilitado, transição, tokens de campo de formulário, shadows de overlay. Severidade/variante/tamanho por componente ficam no CVA de cada um, não aqui.
- [x] **Definir paleta de cor de marca (brand/primary) oficial da Medra** — **Decidido em 2026-07-02**: **Teal** (escala padrão do Tailwind). Remete a crescimento com ar técnico/confiável, evita colisão direta com "emerald" (marca associada ao Supabase no nicho de dev tools). Aplicado em `tailwind-theme-medraui.css`.
- [x] **Estratégia de variantes de componente** — **Decidido em 2026-07-02**: usar **CVA (class-variance-authority)** para compor as classes Tailwind por severidade × variante de estilo × tamanho em cada componente. Lib pequena, madura, framework-agnostic (funciona em Angular normalmente, só retorna string de classes). Suporta "compound variants" para combinações especiais (ex.: outlined+danger). Deve ser combinada com `tailwind-merge` para resolver o escape hatch de customização (item já listado abaixo).
- [x] **Suporte a dark mode** — **Decidido em 2026-07-02**: estratégia por classe `dark` no elemento raiz (`<html>`/`<body>`). O CSS pré-gerado já sai com as regras `.dark ...` embutidas (gerado no build interno da MedraUi); o app consumidor só alterna a classe, sem precisar de Tailwind configurado. Fornecer um snippet JS opcional para inicializar respeitando `prefers-color-scheme` do SO no primeiro load.
- [x] **Pipeline de build** — **Decidido em 2026-07-02**: Tailwind CLI roda **separado** do ng-packagr (que não suporta Tailwind nativamente e duplicaria o CSS por componente se usássemos `styleUrls`). Fluxo: (1) Tailwind CLI escaneia todo código-fonte (templates + strings CVA) e gera um único `styles.css` compilado; (2) ng-packagr compila os componentes normalmente, sem CSS Tailwind embutido; (3) script de build copia o CSS gerado pro `dist/` final antes do publish. CSS exposto via `package.json` `exports` (`./styles.css`), consumidor importa uma vez no nível do app. CSS raro não expressável em utility classes continua no `styleUrls` normal, encapsulado pelo Angular. Em dev, Tailwind CLI roda em `--watch` junto do app de showcase.
- [x] **Escape hatch de customização para o consumidor** — **Decidido em 2026-07-02**: cada componente expõe um `@Input('class')` explícito (string). Internamente mesclamos com as classes geradas pelo CVA via `tailwind-merge`, que resolve conflito de utility classes corretamente (classe do consumidor sempre vence a interna quando colide). Contrato de API documentado: `class` é o caminho suportado e oficial para override; uso direto de `[ngClass]`/`[class.x]` nativo do Angular no host **não** passa por tailwind-merge e não é recomendado para sobrescrever estilo. Criar um helper/base compartilhado (ex.: `mergeClasses()` + base class/composable) para padronizar esse comportamento nos ~90 componentes, evitando reimplementação ad hoc.
- [x] **Estratégia de ícones** — **Revisado em 2026-07-02**: trocado de Lucide para **Heroicons** (lib de ícones open-source, MIT, feita pelo próprio time do Tailwind Labs). Motivo da troca: Heroicons tem variantes nativas *outline*/*solid* (+ mini/micro) que espelham diretamente nosso sistema de variante de estilo por CVA (preenchido/outlined/text), dando mais coerência visual entre ícones e componentes do que Lucide. Integração via **wrapper Angular fino**, mesmo padrão já definido (tamanho via token semântico `--icon-size`, `class`/`tailwind-merge` como escape hatch).
  - **Verificação de cobertura (2026-07-02)**: catálogo real tem 316 ícones. Confirmado que cobre `swatch` (ColorPicker), `funnel` (filtro de Table), `table-cells` (toggle DataView), `command-line` (Terminal), `arrows-right-left` (ImageCompare) — cobertura ~95%+. **Lacuna real encontrada**: não existe ícone dedicado de "alça de arrastar/grip" (usado em OrderList, PickList, reorder de coluna/linha em Table, gutter do Splitter — uns 4-5 componentes). Resolução: manter Heroicons como base e desenhar só esse ícone extra próprio (modelo híbrido pontual, não uma biblioteca paralela completa); revisar outras lacunas pontuais conforme a Fase 3 avançar componente a componente.
  - **Diretriz para desenho de ícones próprios (2026-07-02)**: permitido e viável desenhar ícones 100% próprios (mesmo padrão de wrapper Angular fino, SVG inline, mesma convenção visual do Heroicons — viewBox 24x24, `stroke-width: 1.5`, linecap arredondado). **Proibido usar Font Awesome (qualquer tier, especialmente Pro) como referência de desenho**: ícones Free exigem atribuição CC BY permanente (indesejado); ícones Pro são pagos/proprietários e replicar seu design especificamente é mais próximo de cópia do que inspiração. Referência permitida apenas para conceitos genéricos universais (compartilhados por praticamente todo set de ícones do mercado), nunca o traçado exato de um ícone específico de um set proprietário.

## Fase 2 — Escopo técnico da reescrita
- [x] **Versão mínima de Angular suportada** — **Decidido em 2026-07-02**: **Angular 21+**. Implica: 100% standalone (sem NgModule), APIs de signals (`input()`/`output()`/`model()`/`viewChild()`) como padrão idiomático, componentes zoneless-ready. **Ressalva**: manter **Reactive Forms clássico (ControlValueAccessor)** como integração principal de formulário no lançamento — nosso próprio backlog de bugs (Fase 1) encontrou instabilidade real em Signal Forms mesmo em versões recentes do Angular, então exigir Angular 21+ não resolve isso sozinho. Suporte a Signal Forms entra depois, componente a componente, conforme a API amadurecer.
- [x] **Política de versão Angular alvo para desenvolvimento** — **Decidido em 2026-07-03**, no início da Trilha 1: a MedraUi é desenvolvida e testada sempre contra a **versão LTS mais recente do Angular** (hoje: **21.2.x**), não contra a última versão major recém-lançada (hoje: 22.x, ainda em fase ativa, não-LTS). Motivo prático que gerou a decisão: ao montar o monorepo, o pacote comunitário `@jscutlery/playwright-ct-angular` (necessário para Playwright Component Testing, já que Playwright não tem suporte oficial a Angular) ainda não suporta Angular 22 — sintoma direto de que o ecossistema de terceiros normalmente leva algum tempo para acompanhar uma versão major recém-lançada. Reavaliar o major-alvo cada vez que o Angular promover uma nova versão a LTS (rolling: quando 22.x virar LTS, tornar-se a nova baseline). Não bloqueia suporte a versões mais novas por parte do consumidor final — é só a versão usada internamente para build/CI/testes.
- [x] **Arquitetura do repositório** — **Decidido em 2026-07-02**: **pacote único consolidado** (`@medra/ui`), não um pacote por componente. Estrutura interna tipo monorepo (uma pasta por componente = um secondary entry point do ng-packagr), mas publicado como um só pacote npm com subpaths (`@medra/ui/button`, `@medra/ui/table`...). Tree-shaking resolvido via entry points, sem precisar de ~89 pacotes independentes. App de showcase/docs vive no mesmo workspace mas não é publicado.
- [x] **Stack de testes** — **Decidido em 2026-07-02**: **Jest** para testes unitários/lógica (caminho de migração oficial indicado pelo time do Angular saindo do Karma, ecossistema `jest-preset-angular` maduro) + **Playwright Component Testing** como camada adicional para verificação visual real (estilos computados, screenshot diff local/CI, sem depender de serviço pago tipo Chromatic). Motivo da camada extra: testes unitários com jsdom não verificam se as classes Tailwind/CVA realmente produzem o estado visual esperado (hover/foco/dark mode); dado o peso que estilo tem no produto, vale a garantia extra.
- [x] **Critério de priorização dos componentes** a reescrever — **Decidido em 2026-07-02**: **frequência de uso primeiro**. Pré-requisito não-opcional antes de qualquer componente de tela: construir os primitivos compartilhados (wrapper de ícone Heroicons, base class de `class`+tailwind-merge, serviço de Overlay/Popover, diretiva Ripple). Depois disso, ordem guiada por quão comum o componente é em apps Angular reais — maximiza valor entregue pros primeiros clientes com um subconjunto pequeno de componentes prontos. Lista de tiers concreta a detalhar no item "componentes piloto" da Fase 3.
- [x] **Sistema de ícones**: sem dependência do other icon fonts, substituto definido como **Heroicons** — ver detalhamento na Fase 1
- [x] **Sistema de estilo/CSS**: sem dependência do frameworks de CSS utilitário, **Tailwind v4** (CSS-first, `@theme`) no lugar — ver detalhamento na Fase 1
- [x] **Prefixo de seletor de componente Angular** — **Decidido em 2026-07-02**: **`med-`** (ex.: `<med-button>`, `<med-dialog>`). Descartado `md-` por colisão histórica forte com o AngularJS Material (prefixo literal daquela lib, `md-button` etc.) — usar isso passaria a impressão de lib antiga/descontinuada, contra o pilar de "construído pro Angular moderno". Descartado também `mui-` (colide com Material UI do React) e `mx-` (colide com a própria convenção de utility class do Tailwind).
- [x] **Suporte a i18n** — **Decidido em 2026-07-03**: **sem serviço de tradução próprio da MedraUi**. **Decisão da MedraUi**: adotar só o padrão de `@Input()` direto, descartando o serviço de tradução centralizado — cada componente com texto interno expõe esse texto como `@Input()` com default em inglês; o app consumidor resolve a tradução como quiser (hardcode, ngx-translate, Angular i18n nativo, etc.), sem precisar aprender uma API de i18n própria da MedraUi. Para o **Toast** (API imperativa via serviço, sem binding de template): o texto (ex.: `closeLabel`) é passado por chamada (`toast.show({ message: '...', closeLabel: 'Fechar' })`), com `'Close'` como default se omitido — não haverá um provider de "defaults globais" de Toast. Escopo explicitamente fora: formatação de data/número/moeda por localidade e suporte a RTL ficam de fora por ora, sem necessidade imediata (revisitar se/quando componentes tipo Calendar/DatePicker exigirem).

## Fase 3 — Execução da reescrita
- [x] **Componentes piloto** — **Decidido em 2026-07-02**: **Button, Checkbox, InputText, Dialog, Message/Toast** (após os primitivos compartilhados). Juntos cobrem CVA (severidade×estilo×tamanho), escape hatch de customização, wrapper de ícone, Ripple, `ControlValueAccessor` em duas formas diferentes, correção do bug de binding `false` do Checkbox (backlog Fase 1), serviço de Overlay/Popover + focus trap + camadas/z-index (relevante ao bug de conflito com CDK 22), e padrão de API imperativa via serviço injetável (Toast).
- [x] **Checklist padrão por componente** — **Criado em 2026-07-02** em `checklist-padrao-componente.md`. Consolida todas as decisões das Fases 1-2 num checklist aplicável (sempre + condicional por tipo: formulário/overlay/dados). Só considerar um componente concluído depois de cumprir tudo aplicável aqui. **Reforçado em 2026-07-02**: itens de **acessibilidade** (WCAG 2.1 AA, teste com leitor de tela, contraste) e **responsividade** (breakpoints Tailwind, alvo de toque mobile, comportamento mobile explícito de overlays) expandidos/adicionados — propagado também pros agentes `medra-spec-writer`, `medra-component-implementer` e `medra-component-reviewer`.
- [x] **Padrão de documentação/exemplos novos** — **Decidido em 2026-07-02**: site público construído em **Analog** (meta-framework Angular, mantém tudo na mesma stack, SSR/SSG, identidade visual própria da marca — Teal, medra.dev — em vez de parecer ferramenta interna genérica). Diretriz obrigatória (não é escolha, reforça a regra da Fase 1): **todo texto/prosa e todo exemplo de código/dataset de demonstração é escrito do zero**, nunca copiado de terceiros. Referência de API (inputs/outputs/métodos) gerada automaticamente a partir de comentários TSDoc **próprios** no código-fonte da MedraUi, não extraída/copiada da documentação original. Exemplos interativos ao vivo (não só bloco de código estático), consistente com o padrão atual do mercado (Angular Material, shadcn/ui).

## Fase 5 — Distribuição npm
- [x] **Controle de versão (semver) e changelog** — **Decidido em 2026-07-03**, na Trilha 1: **Changesets** (`@changesets/cli`), não bump manual nem `semantic-release`. Cada mudança relevante ganha um arquivo de changeset (markdown curto: pacote afetado, tipo de bump — patch/minor/major —, descrição em texto original); `changeset version` agrega os pendentes, faz o bump semver e gera `CHANGELOG.md` automaticamente. Motivo: encaixa direto na decisão já registrada de GTM de que "cada componente concluído vira conteúdo de changelog público" — o changelog sai como subproduto natural do processo, não como tarefa extra. Setup técnico: `@medra/ui` (`projects/medra/ui`) virou um npm workspace do monorepo (`workspaces` no `package.json` raiz) para o Changesets conseguir detectá-lo e versioná-lo isoladamente; `access: "public"` no `.changeset/config.json`, consistente com a decisão de npm público (ver abaixo). Scripts adicionados: `npm run changeset` (criar changeset), `npm run version` (aplicar bumps pendentes), `npm run release` (build + `changeset publish`).
- [x] **npm público vs. privado simples** para o pacote — **Decidido em 2026-07-02**: **público**, sem restrição de download.

## Histórico de decisões

### 2026-07-02
- Distribuição via npm é requisito do produto.
- Sem dependência de other icon fonts nem frameworks de CSS utilitário. frameworks de CSS utilitário substituído por Tailwind CSS.
- Nome do produto definido: **MedraUi**. Domínio `medra.dev` já disponível/próprio.

### 2026-07-03
- Início da Trilha 1 (fundação técnica). Workspace Angular criado em `C:\Git\medraui` (fora do OneDrive, decisão do usuário para evitar sincronização de `node_modules`).
- Política nova: MedraUi sempre desenvolvida/testada contra a versão **LTS** mais recente do Angular (não a última major ativa), reavaliada a cada nova LTS. Gatilho: pacote comunitário de Playwright Component Testing para Angular ainda não suportava a v22 recém-lançada no momento do setup.
- Stack de testes ajustada na prática (Trilha 1): Playwright não tem suporte oficial a Component Testing em Angular (só React/Vue/Svelte) e o pacote comunitário encontrado tinha dependência fixa incompatível com Angular 21/22. Decisão final: **Jest** (unitário) + **Angular Testing Library/TestBed** (componente) + **Playwright** (E2E de verdade, contra app real — não Component Testing).
- Controle de versão do pacote `@medra/ui` definido: **Changesets**, com o pacote virando um npm workspace do monorepo. Ver Fase 5 para detalhe completo.
- Trilha 3 (componentes piloto): **Button**, **Checkbox** e **InputText** reescritos e verificados. Checkbox normaliza o valor binário `false`. Tokens de cor de severidade (info/success/warn/help/danger) e tokens de campo de formulário passaram a ser reaproveitados entre componentes.
- i18n: decidido **não construir serviço de tradução próprio** — cada componente com texto interno expõe `@Input()` com default em inglês (ver Fase 2, item "Suporte a i18n" para o detalhe completo, incluindo o caso do Toast).
- **Trilha 3 completa**: Dialog (serviço imperativo sobre o `OverlayService`, sem estender pra `TemplatePortal`) e Message/Toast (Message presentacional simples; Toast imperativo, reaproveitando estilo do Message). `OverlayService` ganhou duas extensões justificadas pelo Toast: `position` (overlay global não-centralizado, ex. canto superior direito) e `closeOnOutsideClick` (antes preso a `!hasBackdrop`, agora configurável — Toast não pode fechar ao clicar na página). Dois bugs reais encontrados e corrigidos no processo: (1) `ViewContainerRef.createComponent()` insere como irmão do elemento-âncora no DOM, não filho — quebrava o padding do conteúdo do Dialog; (2) `position:fixed` duplicado (no host do Toast E no painel do CDK) jogava o stack de toasts pra fora da tela. Backdrop de todo overlay ganhou efeito de blur (`backdrop-blur-sm`) como padrão compartilhado no `OverlayService`, não por componente.

### 2026-07-05
- **Lacuna de i18n de formatação de data/número, registrada como pendente na Fase 2 ("Suporte a i18n"), resolvida**: formatação de valor via string de tokens numéricos (`dateFormat`, ex. `'mm/dd/yyyy'`, reimplementada do zero em `date-format.ts`) e nomes de mês/dia-da-semana via `Intl.DateTimeFormat` nativo (`locale`) — dois inputs independentes, nunca se misturam. Sem dependência nova de data (nenhuma lib tipo date-fns/dayjs entrou no projeto).
- DatePicker reescrito e verificado — arquitetura híbrida entre Select (foco real entra no overlay) e AutoComplete (trigger é `<input>` real, digitável), justificada por ser um widget composto tipo grid (ARIA APG "Date Picker Dialog"). Suporta `selectionMode: 'single' | 'range'` e uma segunda opção de navegação (`navigation: 'calendar' | 'drilldown'`, esta última com fluxo ano→mês→dia) — ambas pedidas explicitamente pelo usuário durante o planejamento, além das 3 perguntas de arquitetura já resolvidas antes de codar (input editável + calendário; range incluído no v1; formato de token numérico ao estilo jQuery UI). Detalhe completo, incluindo os 3 bugs reais encontrados via verificação visual no browser (nenhum pego pelos 56 testes Jest, todos dependiam de layout/CSS computado ou `:hover` real).
- **Rodada 2 do DatePicker, feedback do usuário após testar o showcase**: dois cortes de escopo do v1 (documentados como "não definitivos") foram revertidos e voltaram — `disabledDates`/`disabledDays` (com pulo automático no teclado, não só bloqueio de clique) e placeholder padrão derivado de `dateFormat`. Mais duas adições novas: caixa de busca sempre visível na lista de anos do modo `drilldown` (filtra por substring numérica, mesmo padrão do `filter` do Select mas sempre ligado, não opcional) e largura do painel com piso mínimo de ~19rem que cresce se o campo for mais largo. Reforça o padrão já visto no Toast/Dialog/Menu: revisão manual no browser real continua achando lacunas que os testes unitários (jsdom) não cobrem — aqui, layout/CSS computado e comportamento de `:hover`/foco real.
- **Rodada 3 do DatePicker, mesma sessão de feedback**: mais um corte de escopo revertido — visão de múltiplos meses lado a lado (`numberOfMonths`, configurável, default mode-aware: 2 em range, 1 em single), com colapso responsivo pra 1 mês abaixo do breakpoint `sm`. Bug real encontrado no processo: `new Date(0, mêsAbsoluto, dia)` usado como atalho de aritmética de mês não funciona como esperado — o construtor `Date` do JS trata ano 0-99 como `1900+ano` antes de normalizar mês estourado, gerando datas quase 1900 anos erradas; corrigido com um helper dedicado que calcula ano/mês explicitamente antes de construir o `Date`. Também corrigido: completar um intervalo abrangendo dois meses visíveis não deve resetar a janela pra centralizar só no mês da última data clicada (perderia o mês inicial de vista) — separada a lógica de "seed inicial/drilldown" (sempre recentraliza) da de "nova etapa de range" (só desliza se necessário). Dois ajustes de polimento visual também entraram: placeholder do demo de drilldown corrigido (mostrava texto descritivo em vez do formato digitável) e scrollbar customizada e discreta na lista de anos (no lugar da barra nativa do SO, que destoava do resto da lib).
- **Rodada 4 do DatePicker, mesma sessão**: dois bugs de layout encontrados só ao ver a visão de múltiplos meses de verdade no browser. (1) Dias de meses vizinhos apareciam duplicados (uma vez no grid do próprio mês, outra como preenchimento no grid vizinho) — ao selecionar um intervalo, a mesma data ficava destacada duas vezes, lendo como confuso; corrigido deixando esses dias de preenchimento em branco (sem número, sem interação) sempre que 2+ meses estão visíveis ao mesmo tempo. (2) As linhas da lista de anos do drilldown não acompanhavam a largura real do painel quando o campo era mais largo que o piso mínimo de 19rem — mesmo bug de fundo já visto e corrigido no Select (`.cdk-overlay-pane` é um container flex do Angular CDK, então um filho `block` simples encolhe pro conteúdo em vez de esticar), só que dessa vez no host do próprio `DatePickerPanelComponent`, que tinha `class: 'block'` sem `w-full`. Reforça mais uma vez: bugs de layout/CSS real só aparecem testando no browser de verdade, nunca em jsdom.

### 2026-11-19
- **Mudança de modelo**: a MedraUi deixa de ser um produto comercial e passa a ser uma biblioteca **pública e de código aberto, sob licença MIT**, sem license key, sem cobrança e sem servidor de licença. Removidos o módulo `license` de `@medra/ui` (e a dependência `jose`), o `license-server` e o painel do cliente.
