## Findings

### F-01 [critical] Unapproved library modification (`InputNumberComponent` `min`/`max` widening) violates `proposal.md` Out of scope and Constitution Article V

**Where:** `projects/medra/ui/src/lib/input-number/input-number.component.ts:68-69,125-126,228,233,279,287,329,333,339-340`, `projects/medra/ui/src/lib/input-number/input-number.component.spec.ts`, `docs/changes/document-input-number-parity/proposal.md:20-26,36-37`, `docs/changes/document-input-number-parity/tasks.md:5-7` · `INN-001`, Constitution Article V
**Problem:** `proposal.md:20-21` explicitly places `projects/medra/ui/src/lib/input-number/` under `### Out of scope` ("Any changes to `projects/medra/ui/src/lib/input-number/` (library code and public API are untouched; no changeset required)"), `proposal.md:25-26` classifies the change as `fast`-track documentation-only (`projects/site/` + `e2e/site/`), `proposal.md:37` states `Interfaces: None`, and `tasks.md:5-7` authorizes only `e2e/site/input-number-docs.spec.ts` (`T001`) and `projects/site/` docs (`T002`). Yet `projects/medra/ui/src/lib/input-number/input-number.component.ts` was modified to widen `min` and `max` from `input<number | null>(null)` to `input<number | null | undefined>(null)` and add `?? null` coercion at `aria-valuemin`/`aria-valuemax`, `atMin`, `atMax`, `Home`/`End`, `startingValue()`, and `clamp()`. While this widening is needed for Angular Signal Forms (`@angular/forms/signals`'s `FormUiControl` types `min`/`max` as `InputSignal<number | undefined>` and `cvaControlCreate` binds `fieldState.min?.()` / `fieldState.max?.()` at runtime), `undefined !== null` would otherwise coerce bounds to `undefined`/`NaN`, making this a library public-API and bug-prevention change. Under Constitution Article V, every behavior change and bug fix must be covered by a failing-then-passing Jest test, yet `projects/medra/ui/src/lib/input-number/input-number.component.spec.ts` has no Jest test for `min`/`max` receiving `undefined` or Signal Forms `[formField]` binding, and `tasks.md` has no task for this library edit.
**Fix:** Either (1) bring `projects/medra/ui/src/lib/input-number/input-number.component.ts` into scope by updating `proposal.md` (`Scope`, `Interfaces`, `Impact`) and adding a `[TEST]` task + implementation task in `tasks.md` with red-then-green Jest tests in `projects/medra/ui/src/lib/input-number/input-number.component.spec.ts` covering `min`/`max` set to `undefined` (and `[formField]` binding), or (2) remove the `InputNumberComponent` diff from `document-input-number-parity` and land the Signal Forms `min`/`max` compatibility fix in its own dedicated change first.

### F-02 [major] Missing `@medra.dev/ui` changeset for modified library source (`REQ REL-004`)

**Where:** `.changeset/`, `projects/medra/ui/src/lib/input-number/input-number.component.ts:125-126` · `REQ REL-004`, Constitution Article X
**Problem:** `docs/specs/release-versioning/spec.md:63` (`REQ REL-004`) requires a changeset whenever a change modifies published package source under `projects/medra/ui/` (other than tests-only), or the PR changeset gate (`tools/release/check.mjs`) fails. Because `projects/medra/ui/src/lib/input-number/input-number.component.ts` was modified and `.changeset/` currently contains only `.changeset/date-picker-parity.md` (for `DatePicker`), no changeset covers the `InputNumberComponent` `min`/`max` change.
**Fix:** If `projects/medra/ui/src/lib/input-number/input-number.component.ts` stays in this change, add a `.changeset/*.md` file for `@medra.dev/ui` using a `patch` (or `minor`, never `major` per Constitution Article X) bump describing the `min`/`max` `undefined` support for Signal Forms; otherwise revert the library edit from this change and carry the changeset in the dedicated library change.

### F-03 [minor] `input-number-fluid.txt` states `fluid` opts into full-width layout while `InputNumberComponent.fluid` is unused

**Where:** `projects/site/src/content/docs/input-number-fluid.txt:3`, `projects/medra/ui/src/lib/input-number/input-number.component.ts:141,164-176,195-200`, `projects/medra/ui/src/lib/input-text/input-text.styles.ts:18` · `INN-001`
**Problem:** `projects/site/src/content/docs/input-number-fluid.txt:3` states: `` `fluid` opts the field into full-width layout so the spinbutton fills the width of its container. `` In `InputNumberComponent`, `readonly fluid = input(false, { transform: booleanAttribute })` (`line 141`) is declared, `hostClass()` (`lines 164-176`) unconditionally returns `'block w-full'`, `'flex w-full'`, or `'flex flex-col w-full'`, `inputTextVariants` (`input-text.styles.ts:18`) unconditionally includes `'w-full'`, and `this.fluid()` is never read anywhere in the component (nor is `MED_FLUID_CONTEXT` injected). Claiming `fluid` "opts the field into full-width layout" inaccurately implies the spinbutton is not full-width without `fluid`.
**Fix:** Update `projects/site/src/content/docs/input-number-fluid.txt:3` to document accurately that `med-input-number` fills the width of its container by default (`w-full`) and accepts `fluid` for form-control API parity (or implement opt-in `fluid` sizing in a separate library change).
