**Stage:** verify

## Summary

Both `DAT-050` (`breakpointMode="container"`) and `DAT-060` (`data-med-stack-sort`) are implemented in `DataTableComponent` with passing Jest unit tests (`T001` red, `T002` green, `Suite: green`), verified user-authorized test edits on `T002`, and clean audit results on the CLI-flagged specs. However, the change fails verification due to a Constitution Article V violation without Complexity Tracking: layout-dependent `DAT-050.S7` (`ResizeObserver` container stacking) and `DAT-060.S1` (visible stacked sort bar) have no real-browser verification (Playwright or showcase), and neither existing responsive-stack Playwright spec was run. In addition, the native `<select>` in `data-med-stack-sort` fails to display a pre-existing `sortField`/`multiSortMeta` on initial stack render and desyncs when `removableSort` is `false`, and several `REQ DAT-060` clauses (`sortMode="multiple"`, `lazyLoad`, label overrides, render gating) lack unit tests.

## Findings

### F-01 [critical] Constitution Article V violated without Complexity Tracking: no real-browser verification for `DAT-050.S7` or stacked sort UI

**Where:** `docs/changes/data-table-responsive-stack-enhancements/tasks.md:7-10`, `projects/medra/ui/src/lib/data-table/data-table-responsive-stack-enhancements.spec.ts:40-100`, `e2e/site/data-table-responsive-stack.spec.ts` · `DAT-050` (`DAT-050.S7`), `DAT-060` (`DAT-060.S1`), Constitution Article V
**Problem:** Constitution Article V (`docs/constitution.md:40-42`) mandates that behavior depending on computed layout, CSS, or real focus be verified in a real browser (showcase or Playwright test) because jsdom does not cover it, and `docs/changes/data-table-responsive-stack-enhancements/proposal.md` contains no Complexity Tracking justifying an exception. Scenario `DAT-050.S7` (`specs/data-display/spec.md:62-66`) tests `ResizeObserver`-driven container stacking inside a wide viewport and block/table CSS layout transitions, yet `data-table-responsive-stack-enhancements.spec.ts:44-99` mocks `ResizeObserver` with `MockResizeObserver`, manually invokes `hostObserver!.cb(...)`, and asserts only `classList.contains('block')` in jsdom (whereas `data-table.component.spec.ts:5522` notes jsdom cannot measure CSS rules and `DAT-050.S1`–`S4` are verified in `e2e/site/data-table-responsive-stack.spec.ts:27-94`). Similarly, `DAT-060.S1`'s visible `data-med-stack-sort` bar has no real-browser check for computed layout, visibility, focus ring, or dark-mode appearance, and the existing `e2e/site/data-table-responsive-stack*.spec.ts` suites were not run even though `projects/site/src/app/pages/docs/components/demos/data-table-responsive-stack.demo.html:11-12,41` has `[sortable]="true"` columns where `data-med-stack-sort` now renders.
**Fix:** Add Playwright real-browser verification covering `DAT-050.S7` (`breakpointMode="container"` container resizing across `breakpoint` with computed `display: block`/`table`) and `DAT-060.S1` (visible `data-med-stack-sort` sorting, focus visibility, and dark-mode styling), run `npx playwright test --reporter=list --project=site e2e/site/data-table-responsive-stack*.spec.ts` (and the new test), and record the task/evidence in `tasks.md`.

### F-02 [major] Stacked sort `<select>` drops pre-existing `sortField`/`multiSortMeta` on initial stack render and desyncs when `removableSort` is `false`

**Where:** `projects/medra/ui/src/lib/data-table/data-table.component.ts:586-596, 3225-3230, 3255-3266` · `DAT-060`
**Problem:** Two defects affect the native `<select>` inside `data-med-stack-sort`:
1. Line `588` binds `[value]="activeStackSortField()"` on `<select>` while lines `593-595` generate `<option [value]="col.field()">` inside `@for` without `[selected]`. In Angular's template update order, `<select>.value` is assigned before `@for` inserts the column `<option>` elements into the DOM; when `@if (stacked() && sortableVisibleColumns().length > 0)` first mounts with a pre-existing `sortField` or `multiSortMeta` (e.g., narrowing from desktop after sorting, initial sorted state, or `stateKey` restore), only `<option value="">` exists at assignment time, so `<select>.value` resets to `""` (`"Sort by"`) even while `activeStackSortField()` is non-empty and the direction/clear buttons render beside it.
2. When `removableSort()` is `false`, line `607` hides `data-med-stack-sort-clear`, but line `592` leaves `<option value="">{{ stackSortLabel() }}</option>` enabled. Selecting that option invokes `onStackSortFieldChange` -> `clearStackSort()`, which returns early (`line 3256`) without changing `activeStackSortField()`; because the signal value did not change, Angular does not reset `<select>.value`, leaving the `<select>` showing `"Sort by"` while the table remains actively sorted.
**Fix:** Bind `[selected]="col.field() === activeStackSortField()"` on each `@for` `<option>` (and `[selected]="activeStackSortField() === ''"` on the placeholder `<option>`), bind `[disabled]="!removableSort() && activeStackSortField() !== ''"` on the placeholder `<option>`, and in `onStackSortFieldChange` reset `(event.target as HTMLSelectElement).value = this.activeStackSortField()` if `!field && !this.removableSort()`. Add Jest tests covering entering stacked mode with pre-set `sortField`/`multiSortMeta` and `removableSort="false"`.

### F-03 [major] Untested `REQ DAT-060` clauses (`sortMode="multiple"`, `lazyLoad`, label overrides, render gating) and missing ascending `sort` emission check in `DAT-060.S1`

**Where:** `projects/medra/ui/src/lib/data-table/data-table-responsive-stack-enhancements.spec.ts:102-166` · `DAT-060` (`DAT-060.S1`), Constitution Articles VIII & XI
**Problem:** `REQ DAT-060` (`specs/data-display/spec.md:9`) specifies rendering `data-med-stack-sort` only when `stacked()` is `true` and at least one visible column is `sortable`, customizing `stackSortLabel`/`stackSortAscLabel`/`stackSortDescLabel`/`stackSortClearLabel`, updating `multiSortMeta` in `sortMode="multiple"`, and triggering `lazyLoad` in `lazy` mode. None of these requirements are tested in `data-table-responsive-stack-enhancements.spec.ts` (including no test verifying `data-med-stack-sort` is absent when unstacked or when the only sortable column has `visible="false"`). In addition, `DAT-060.S1` (`lines 139-158`) only checks `sortEvents.at(-1)` after clicking `data-med-stack-sort-dir` and omits asserting that `sort` emitted on the initial ascending column selection (Constitution Article XI).
**Fix:** Extend `data-table-responsive-stack-enhancements.spec.ts` to assert: (1) `sort` emission on initial ascending selection in `DAT-060.S1`, (2) `sortMode="multiple"` updating and clearing `multiSortMeta` + emitting `sort`, (3) `lazy` mode emitting `lazyLoad` on stack sort selection/toggle/clear, (4) custom `stackSortLabel`, `stackSortAscLabel`, `stackSortDescLabel`, and `stackSortClearLabel` overrides, and (5) `data-med-stack-sort` omitted when unstacked or when no visible column is `sortable`.

### F-04 [minor] Container-mode `breakpointPx` rejects leading-dot decimals and resolves `em` against root `fontSize` instead of host `fontSize`

**Where:** `projects/medra/ui/src/lib/data-table/data-table.component.ts:28, 1347-1360` · `DAT-050`
**Problem:** `CSS_LENGTH_PATTERN` (`line 28`) uses `^\d*\.?\d+` (accepting `.5rem`), whereas `breakpointPx` (`line 1349`) uses `/^(\d+(?:\.\d+)?)(px|em|rem)$/i` and multiplies both `em` and `rem` by `getComputedStyle(document.documentElement).fontSize` (`lines 1358-1359`). Consequently, `.5rem` stacks in `'viewport'` mode but is treated as invalid in `'container'` mode, and `em` in `'container'` mode ignores the host element's computed font size.
**Fix:** Align the numeric pattern in `breakpointPx` to `^\d*\.?\d+` and resolve `em` against `getComputedStyle(this.host.nativeElement).fontSize` (falling back to root/16px), reserving `document.documentElement` for `rem`.
